  1. 面向智能体的库湖一体引擎开始落地

总判断：数据平台的职责继续外移：一边为智能体提供库湖一体的数据底座与受控接口，一边承接用量与成本治理；另一头，算力的约束已从需求侧移到供给侧，电力、内存与封装在 2027 年前都是硬约束，长期承诺算力价格的前提需要重估。

火山引擎 Lakebase 正式发布：面向 Agent 的库湖一体数据引擎

来源： 字节跳动技术团队 / 火山引擎产品文档
摘要： 火山引擎 10 月 22 日发布面向 Agent 的库湖一体数据引擎 Lakebase，数据以开放湖表格式存放在对象存储上，Serverless 存算分离按需拉起算力，定位是「轻量又完整」，入湖、转换、查询、管理走同一条链路。官方文档给出的机制是以 PostgreSQL 为事务底座，业务数据一次写入，系统自动生成主流湖仓格式的分析表，再由统一 Catalog 完成治理，全程无需 ETL 与同步管道。四大能力分别是业务数据自动转换、多源数据入湖、弹性算力与海量数据资产管理，官方称算力成本可降 90% 以上。
为什么对数据平台重要： 这是把「库湖一体」的产品目标从人和报表改写为智能体的一次直接动作：Agent 需要同时访问 OLTP 实时数据与湖表历史数据，而企业数据中约 80%–90% 是散落在业务系统与外部平台的非结构化内容，官方援引的预测是 2026 年约 60% 的 AI 项目可能因数据处理问题被放弃。若 Zero ETL 与统一 Catalog 能如期兑现，同一份数据可同时服务在线事务、实时分析与 AI 应用，数据平台的接入与同步管道成本会被显著压缩。选型口径也随之改变：真正要比的是智能体获取上下文的端到端成本，而不只是查询性能；90% 的降本数字为厂商口径，需要用自有负载验证。

Snowflake 发布 Agentic Analytics 架构：Ground、Analyze、Act 三支柱加 Assure 治理

来源： Snowflake 官方博客
摘要： Snowflake 10 月 22 日发布《Agentic Analytics: Building a Data Foundation for AI Agents》，把服务智能体的平台能力归入 Ground、Analyze、Act 三支柱，并由贯穿三者的 Assure 治理层收口。Ground 用 Horizon Context、语义视图与 Cortex Search 提供机器可读的业务上下文，Data Metric Functions 监控完整性与唯一性，Dynamic Tables 对齐新鲜度目标；Analyze 用编译器与优化器、Gen 2 与 Adaptive Warehouses 上的 Optima、Interactive Analytics 承接路径未知的迭代式查询；Act 通过 Workflows 与 MCP connector 把结论交回业务系统，Assure 负责访问控制、Agent 会话限额与查询留痕，同日官方举办同名线上研讨会。
为什么对数据平台重要： 这是一份写给平台负责人的接口清单：MCP、语义视图与 SQL 对象被放在同一层作为互操作界面，官方明确反对把数据复制进每一个 AI 平台。对自研或采购团队，评估项随之改变——语义层能否被外部 Agent 直接消费、访问控制是否附着在数据而非会话上、Agent 产生的查询是否进入既有的成本与审计口径，都是能不能进生产的前提。把 Agent 查询当作独立负载类别来供给能力（Optima 依观测负载自动调优、Interactive Analytics 承接高并发低延迟），比单纯宣称支持 Agent 更值得评估。

IDC：AI 基础设施的约束已从需求侧转到供给侧

来源： IDC 官方博客
摘要： IDC 首席研究官 Meredith Whalen 10 月 22 日撰文指出，95.3% 的企业已有至少一个 Agent 工作流在生产环境运行、平均约 11 个，IDC 预计 2030 年 Agent 数量将达 25 亿，需求侧仍然强劲；约束在供给侧：数据中心机架将从 2026 年的 2500 万增至 2030 年的 5800 万，能耗从 2025 年的 519 TWh 升至 1308 TWh，而同期 AI 基础设施支出增长 3.35 倍，仅美国就有近 7 GW 的 2026 年计划容量因缺电延期或取消。内存与封装同样紧张：2026 年 DRAM 供给增速预计仅 16%、NAND 为 17%，HBM4 供给要到 2027 年中才追得上需求，ABF 载板在 2027 年下半年前难有实质新增；IDC 的结论是供给而非需求决定节奏，稀缺的产能会持续推高单位价格。
为什么对数据平台重要： 关键在时间尺度错配——AI 数据中心的选址与建设需要 5 到 7 年，而其中的加速卡 12 到 18 个月就换一代，把算力当成可长期持有的资产会在折旧节奏上失真；IDC 同时指出真正耐久的资产是数据中心场地与并网容量，加速卡老化后会流入二手市场。这条直接约束采购口径：长约锁量与现货采买要按供给紧张期来算，自建与租用要按单位任务成本而非单卡价格比较，而模型路由与推理内存管理带来的 30%–60% 成本下降，应先于扩容决策落地。存量合同与扩容计划需要重新过一遍供给假设。

BigQuery AI.TRANSLATE 正式可用：翻译能力以 SQL 函数进仓

来源： Google Cloud 官方发布说明
摘要： Google Cloud 10 月 22 日的发布说明记录，BigQuery 的 AI.TRANSLATE 函数正式可用，可在 SQL 中直接翻译文本字符串，同时支持标准神经机器翻译（NMT）负载与翻译大模型（TLLM）两条路径。同一份发布说明还记录 Data Studio 可以连接 BigQuery Graph，或用自定义 SQL 查询图数据，并把图度量导入报表作为指标使用。
对数据平台的影响： 多语言文本处理此前要么在仓外调用翻译服务再回写，要么在下游 BI 里二次加工；函数进仓后，翻译可以作为视图或物化表的一步，与其他转换共享同一套权限、配额与审计。对平台团队更实际的影响在成本结构上：神经机器翻译与翻译大模型两条路径并存，意味着同一类作业可以在质量与单价之间切换，翻译任务开始具备按单位成本做路由的条件。另一处变化是图数据进入报表层，BigQuery Graph 的度量可以被 Data Studio 直接消费，图分析与多模态分析正在共用同一套语义与权限框架。

Amazon OpenSearch Serverless 推进摄取与可见性：默认刷新间隔降至 5 秒，新增 S3 摄取接口

来源： AWS 最新公告 / AWS API 变更归档（10-22 批次）
摘要： AWS 10 月 22 日公告，下一代 Amazon OpenSearch Serverless 的搜索集合与向量集合默认刷新间隔由 10 秒缩短至 5 秒，读后写可见性随之提升，适用于全文检索、检索增强生成、语义搜索、推荐与个性化场景，已覆盖该服务可用的全部 24 个区域。同日的 API 变更批次新增了从 S3 向 OpenSearch Serverless 集合写入的摄取作业与摄取流管理接口，支持创建、查询、列举与取消摄取作业，以及创建、查询、列举与删除摄取流。
对数据平台的影响： 检索与向量索引正在从「自建同步管道」转向「云侧托管摄取」，对象存储落一份数据即可生成摄取作业或持续流，省掉的是中间缓冲与同步运维这一段；但摄取作业与摄取流同时是新的可观测对象，落地时必须把数据新鲜度、失败重试与增量边界纳入监控，否则检索层会出现「看起来有数据、其实滞后」的问题。默认刷新间隔从 10 秒降到 5 秒，直接影响依赖检索结果的实时链路：接近实时的读写一致性要求可以放宽，但引用时效性字段的报表与 Agent 工具调用仍需要按更短窗口重算。

AWS Glue 纳入大规格 worker 类型：内存密集型作业不必再靠堆节点换内存

来源： AWS SDK for Kotlin v1.9.24 发布说明（10-22） / AWS API 变更归档（Glue）
摘要： AWS 10 月 22 日的 API 变更批次中，Glue 新增了对大规格 worker 类型的支持，官方变更记录表述为 add support for large worker types in AWS Glue，同日发布的官方 SDK 版本说明同步列出该项。Glue 文档当前的 WorkerType 枚举已包含 G.1X 至 G.96X 与 R.1X 至 R.96X，其中 G.12X 及以上与对应的 R 系列属于文档所称的大规格，文档同时说明大规格由 Glue 5.0 引入，本次变更的意义在于这类规格被正式纳入 API 变更范围。
对数据平台的影响： 内存优化型的大规格实例给 Spark 作业提供了一条新的扩容路径：过去内存不足只能横向增加节点数，单机内存上限本身就是一道墙，作业规模一大就被迫拆分或降级精度。对平台团队值得做的事是把内存密集型作业挑出来重新评估节点数与单机规格的比价——大宽表聚合、状态型 join、批量特征计算是优先对象，但前提是先量清楚这些作业的真实内存占用，否则换规格只会放大闲置；大规格同时意味着单次失败的影响面更大，作业级配额、重试与超时策略需要一并重算。

Databricks：AI 账单是结构性的，工程组织需要一层控制面

来源： Databricks 官方博客
核心观点： Databricks 10 月 22 日发布对联合创始人 Patrick Wendell 的访谈《The AI Bill is coming》。核心判断是 AI 工具按用量计费会带来结构性指数增长：无限 token 与硬性封顶两种做法都失败了，封顶会把最重度用户在任务中途切断，逼他们转用个人账号，反而失去可见性。官方给出四个杠杆——默认使用更高效模型、把任务路由到最便宜的可用模型、让开发者看到自己的花费、削减 token 开销，宣称最多可降低 90% 成本（厂商口径）；关键机制是 token 单价不是模型真实成本的好预测，因此每个工程组织都需要一层位于开发者与模型之间的控制层，Databricks 内部的实践演化为 Unity Gateway。他们最终采用可见性加渐进摩擦（先警告、再审批、再降级到更便宜模型），目前人均 token 支出已持平，而总用量与产出价值仍在上升。
映射到数据平台的判断： 把「AI 用量的成本控制」放在数据平台旁边讨论，实质是指出一个新的平台位置：网关层既要管访问与路由，又要给出可观测的账单口径，而这两件事都建立在同一套调用元数据上。数据平台已有的目录、权限与用量统计能力天然能承接这一层——把模型、工具、上下文与成本打上同一套目录标签，才能回答「哪类任务消耗了多少、是否值得用更贵的模型」。对采购与自研的判断标准也随之变化：数据平台要不要内置 AI 网关能力，或至少保证自己的元数据能被网关及其账本复用，这已经不是可选项。

ClickHouse 用 Langfuse 承接智能体轨迹：Agent 运行数据成为一类新的分析负载

来源： ClickHouse 官方博客
核心观点： ClickHouse 10 月 22 日发布技术文章，演示把 Cursor 编码智能体的每一次模型调用、工具执行与 token 用量通过 Langfuse 的 Observability 插件采集为 trace，再由 ClickHouse 作为分析底座承接。Langfuse v4 用一张宽表把用户、会话、标签与环境和每条 observation 放在一起，仪表盘与 Metrics API v2 直接按用量、成本与延迟聚合，避免 join trace 表与 observation 表；文中给出团队定位高成本 turn、把重复上下文写成项目规则、再用 LLM-as-a-judge 评估前后差异的闭环，以及用 GitHub Action 在 CI 阶段卡住评分不达标的实验。
映射到数据平台的判断： 文章示范的是一类新负载：智能体轨迹是「每次会话产生一批高基数字段」的事件流，既要按单个 run 排查，也要按团队、模型与时间做趋势汇总，「明细可下钻、汇总要跑快」的双重要求正是列式 OLAP 的主场，这也解释了智能体可观测平台为什么把底层让给分析型数据库。对数据平台团队的含义是，Agent 运行数据的留存与归因需求会持续挤压现有数仓的模型设计，token 成本、工具调用次数与上下文重复率会变成与业务指标并列的运营指标，值得提前规划分区、保留策略与成本口径的位置，而不是等数据量涨起来再补表。

【收购兼并】LSEG 以 35.35 亿美元全现金收购 Octus

来源： LSEG 交易公告（RNS 0343A） / Permira 公告
核心数据： 交易对价 35.35 亿美元全现金，卖方为 Permira 顾问基金与 Octus 管理层（含创始人 Kent Collier）。Octus 2026 年预计收入超 3 亿美元、调整后 EBITDA 利润率约 40%，2022 年以来收入保持双位数复合增长；服务 750 家客户、超 4 万名个人用户、员工超 900 人。私募信贷市场规模约 3.5 万亿美元，私募市场数据、工作流与接入方案市场规模为 70 亿至 90 亿美元。据 Permira 口径，Octus 在 2026 年内执行了超过 400 万次自动分类、100 万次结构化数据抽取与超过 25 万次内容摘要生成。交易预计 2027 年上半年完成。
摘要： LSEG 10 月 22 日宣布以全现金收购私募与非流动信贷情报数据商 Octus。Octus 2013 年由 Kent Collier 成立于纽约，核心动作是把难获取的信贷文件（契约条款、交易条款等）转成结构化、可检索、可被 Agent 直接调用的数据，客户通过其平台、MCP connector 或 AI 工作流三种方式接入。交易完成后 Octus 并入 LSEG 数据与分析部门，创始人继续领导该业务；LSEG 另在同日发布第三季度经营更新。
对数据平台的影响： 这笔交易把「把非结构化文档变成可被 Agent 直接调用的结构化数据」明确定价为可交易的核心资产：一年超过 400 万次自动分类、100 万次结构化抽取与 25 万次内容摘要，说明文档智能本身已经是可计量的服务，而不是数仓的附属功能。对平台团队有三点可迁移的判断：其一，非结构化文档的结构化服务本身就是数据产品，不必依附于数仓存在；其二，MCP connector 正在成为数据产品的新交付形态，接入方式的变化会反过来决定接口设计；其三，公开市场之外的数据（私募市场约 3.5 万亿美元规模）正在按 70 亿至 90 亿美元的市场空间被定价，数据供给的竞争正转向「谁能被 Agent 稳定消费」，而不只是「存了多少数据」。

【跟踪】VAST Data 与 NVIDIA 发布 Agent Sandbox 基础栈：智能体算力短暂、状态持久

来源： VAST Data 官方新闻稿 / VAST Data 官方博客
为什么值得继续看： VAST Data 与 NVIDIA 10 月 21 日发布 Agent Sandbox Foundation Stack，把智能体沙箱的环境搭建、状态持久与审计拆成三层：VAST AI OS 用零拷贝克隆为 OpenShell 沙箱秒级供给持久存储，DataStore 提供沙箱存储与快照，DataBase 提供共享记忆、上下文与企业数据访问，Management System 给出实时可见性，DataBase 持久记录每一次工具调用、提示词、token、成本与决策。厂商主张是「智能体算力可以短暂，智能体状态必须持久」，沙箱与算力节点解耦后，智能体可暂停、恢复或在可用基础设施之间迁移而不丢进度。官方新闻稿 dateline 与博客发布时间均为 10 月 21 日，新加坡当地媒体报道为 10 月 22 日，日期口径存在一天差异，本期按跟踪处理。
需要等待什么信号确认： 等待官方计划公开的自动化部署 GitHub 仓库上线，以及首个可核验的客户规模案例与定价口径；同时关注这套「状态持久 + 不可变审计」的分层是否会被其他存储与数据库厂商跟进——如果 Agent 的状态与审计成为独立产品类别，数据平台的职责边界会再一次外扩，需要提前判断哪些能力应该自建、哪些应该纳入采购。
